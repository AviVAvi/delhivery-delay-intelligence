# Delhivery Last-Mile Delay Intelligence Pipeline

Capstone project, Artificial Intelligence and Machine Learning Certification Program, E&ICT Academy, IIT Roorkee
**Author:** Asmit Bohra

The regional operations head has three open questions: how long a parcel will really take (Part B), which parcels will miss their promise (Part C), and which hubs need which playbook (Part D). This repository answers all three with one connected pipeline. The cleaning and feature code from Part A feeds every later Part, and the final scoring script combines the Part C classifier with the Part D hub segments to turn a batch of new parcels into an action list.

The data is synthetic and is produced by `generate_data.py`. No real Delhivery shipment records are used.

## Pipeline

| Step | Script | Reads | Writes |
|---|---|---|---|
| Data | `generate_data.py` | none | `data/hubs.csv`, `data/raw_shipments.csv`, `data/new_shipments.csv` |
| A | `part_a_clean_eda.py` | raw shipments, hubs | `data/modelling_table.csv`, `outputs/part_a_checks.csv`, `outputs/part_a_delay_by_group.csv`, `outputs/part_a_correlations.csv` |
| B | `part_b_regression.py` | modelling table | `outputs/part_b_checks.csv`, `part_b_tree_depth.csv`, `part_b_metrics.csv`, `part_b_gb_learning_rate.csv`, `part_b_cv.csv` |
| C | `part_c_classification.py` | modelling table | `outputs/part_c_models.csv`, `part_c_feature_scores.csv`, `part_c_selectk.csv`, `part_c_tuning.csv`, `part_c_thresholds.csv`, `part_c_final_test.csv`, `part_c_final_config.csv` |
| D | `part_d_segments.py` | modelling table, hubs | `outputs/hub_profile.csv`, `part_d_separation.csv`, `hub_segments.csv`, `segment_profile.csv`, `tier_vs_segment_mismatch.csv` |
| D | `package_model.py` | Part C final config, modelling table, raw shipments | `models/delay_model.pkl`, `delay_threshold.csv`, `feature_order.csv`, `impute_values.csv`, `outputs/part_d_reload_check.csv` |
| D | `predict_delay.py` | new shipments, hubs, `models/`, hub segments | `outputs/new_shipment_actions.csv` |

`src/shipment_prep.py` holds the pinned constants (`PROMISED_HOURS`, `FEATURES`, `NOISE_COLUMNS`) and the two shared functions `clean_shipments` and `build_features`. Part A, `package_model.py` and `predict_delay.py` all import them, so there is only one copy of the cleaning logic.

## How to run

Requires Python 3.11 to 3.13 (developed and tested on Python 3.13). From a fresh clone, run these commands in order from the repository root:

```bash
git clone https://github.com/AviVAvi/delhivery-delay-intelligence.git
cd delhivery-delay-intelligence
python -m venv .venv
source .venv/bin/activate        # on Windows: .venv\Scripts\activate
pip install -r requirements.txt
python generate_data.py          # prints: 24 1224 48
python part_a_clean_eda.py
python part_b_regression.py
python part_c_classification.py
python part_d_segments.py
python package_model.py
python predict_delay.py
```

- `models/delay_model.pkl` is regenerated by running `python package_model.py`. The committed pickle loads reliably only on the scikit-learn version pinned in `requirements.txt` (1.5.2). If the installed versions differ, re-run `package_model.py` instead of loading the committed pickle. It is already in the run order above, before `predict_delay.py`.
- `requirements.txt` pins pandas, numpy, scikit-learn and joblib with `==`. It also pins scipy, which scikit-learn uses internally. scikit-learn 1.5.2 passes an optimizer option that scipy 1.18 no longer accepts, so scipy is held at 1.17.1.
- Every split, model and search uses the pinned `random_state`, so each script writes the same files on every run. Running `predict_delay.py` twice produces byte-identical output.

## Data findings

**Cleaning** (`outputs/part_a_checks.csv`). The raw export has 1224 rows. Removing 24 exact duplicates leaves 1200 shipments, and all 1200 survive the hub merge. Before filling, after removing duplicates, the gaps were:

- 36 missing `distance_km`
- 24 missing `parcel_weight_kg`, plus 5 scanner-fault sentinel weights (999 kg) that are also treated as missing
- 12 missing `declared_value`
- 18 missing `payment_mode`, which become `Unknown`

`service_type` had 12 different spellings, which cleaning reduces to 3. The gaps are filled with medians: 314.95 km for distance, 1.83 kg for weight and INR 1,121.50 for declared value. After cleaning there are 0 missing values across the 17 features and the target. 278 parcels are delayed, a delay rate of 0.2317. For `delivery_hours` the IQR rule gives Q1 = 43.255 and Q3 = 72.5625, so the bounds are -0.7063 and 116.5238. Only 1 parcel falls outside them, and it stays in the table.

**Findings** (`outputs/part_a_delay_by_group.csv`, `outputs/part_a_correlations.csv`)

1. **Express is delayed most often.** 119 of 243 Express parcels miss their promise, a delay rate of 0.4897, against 0.2056 for Standard and 0.0857 for Economy. Express has the tightest promise (36 hours) and a mean delivery time of 36.8056 hours. On average it arrives right at the promise, so about half its parcels land on the wrong side. Economy parcels take 82.0931 hours on average, well inside their 96-hour promise.
2. **The delay rate climbs steeply with hub tier.** It rises from 0.0400 at Tier 1 (16 of 400) to 0.2150 at Tier 2 (86 of 400) and 0.4400 at Tier 3 (176 of 400). Mean delivery time over the same tiers is 48.5664, 58.8194 and 63.4943 hours.
3. **Distance is the sharpest single divider.** The delay rate is 0.0219 for 0-200 km (6 of 274), 0.1368 for 201-400 km, 0.4364 for 401-600 km and 0.8523 for 601+ km (75 of 88). Beyond 600 km most parcels miss their promise.
4. **Three columns correlate most strongly with `delivery_hours`** (ranked by absolute correlation, excluding `delivery_hours` itself):

   | Column | Correlation |
   |---|---|
   | `promised_hours` | +0.8372 |
   | `distance_km` | +0.4013 |
   | `n_stops` | +0.3247 |

   `hub_daily_capacity` (-0.3237) and `hub_tier` (+0.3175) come next. `promised_hours` ranks first because it encodes the service type: Economy parcels take the most hours but rarely miss. For the delay question itself, distance matters more: corr(`is_delayed`, `distance_km`) = 0.5455.
5. **`declared_value_inr` was log-transformed because it is strongly right-skewed.** In the median-filled column the mean is INR 1,533.05, far above the median of INR 1,121.50, so a few very expensive parcels pull the mean up. After the natural log, the mean (7.0277) and median (7.0224) are almost equal. The skew is gone, and the extreme values no longer dominate scale-sensitive models such as the scaled linear and logistic regressions.

## Model results (regression)

The split is 840 / 180 / 180 rows (`outputs/part_b_checks.csv`). The scaler is fitted on the training rows only. The largest absolute column mean of the scaled training rows is 0.0, while for the scaled test rows it is 0.2187, which shows that no test information reached the scaler.

**Validation scores** (`outputs/part_b_metrics.csv`)

| Model | MAE | RMSE | R² |
|---|---|---|---|
| mean_baseline | 15.7952 | 18.8552 | -0.0212 |
| linear_regression | 3.9222 | 4.8912 | 0.9313 |
| gradient_boosting | 3.9166 | 4.9165 | 0.9306 |
| random_forest | 4.2794 | 5.5059 | 0.9129 |
| decision_tree (depth 6) | 5.0971 | 6.2796 | 0.8867 |

- **Baseline.** Predicting the training mean for every parcel gives R² = -0.0212 on validation. A single number explains none of the variation in delivery time. R² is slightly below zero because the validation mean differs a little from the training mean. Its RMSE of 18.8552 hours is the "do nothing" error that every real model has to beat.
- **Validation winner.** Linear regression has the lowest validation RMSE: 4.8912 hours (R² 0.9313). Gradient boosting is just behind at 4.9165 hours.
- **Tree depth** (`outputs/part_b_tree_depth.csv`):
  - **Depths 1–3 are high bias.** Training and validation errors are both high and close together: 11.6334 vs 12.1324 at depth 1 (a gap of about 0.5 hours), and 7.5295 vs 8.7033 at depth 3. The tree is too simple to fit even the training data.
  - **Depths 4 and 6 are the balance point.** Depth 6 has the lowest validation RMSE, 6.2796 (train 4.7114), so it is the depth used for the decision tree above.
  - **Depths 8, 12 and unlimited are high variance.** Training RMSE keeps falling (3.336, 1.3613, 0.0) while validation RMSE rises (6.7901, 7.354, 7.8368). The unlimited tree memorises the training rows exactly (train RMSE 0.0) and has the largest gap.
- **Learning rate** (`outputs/part_b_gb_learning_rate.csv`):
  - **0.1 is best,** with validation R² 0.9306 (RMSE 4.9165).
  - **0.01 is too slow.** Each of the 100 trees adds only 1% of its correction, so after 100 rounds the model is still far from the target and underfits (R² 0.7127, RMSE 10.0018).
  - **1.0 overshoots.** Each tree applies its full correction, so the model chases the noise in individual residuals and steps past the optimum (R² 0.844, RMSE 7.3701).
- **Cross-validation and the model I would ship** (`outputs/part_b_cv.csv`). Both top models were run through the same `KFold(n_splits=5, shuffle=True, random_state=42)` object on the 1,020 training-plus-validation rows. Mean R² was 0.9261 (std 0.0048) for linear regression and 0.9353 (std 0.0045) for gradient boosting, so the two rankings disagree. On the single 180-row validation set the two models were practically tied, about 0.03 hours of RMSE apart. Across five different held-out folds, gradient boosting is ahead by about 0.009 R², roughly twice the fold-to-fold standard deviation. **I would ship gradient boosting**, for two reasons:
  1. Cross-validation uses all 1,020 rows and five different held-out sets, so it is a steadier estimate than one small split.
  2. `generate_data.py` contains interaction effects that a tree ensemble learns on its own but a plain linear model cannot represent without hand-made interaction columns: the sale window adds 12 extra hours to Express parcels only, and rain adds 8 extra hours only on lanes over 400 km.

  Following the pinned rule, the test row in `part_b_metrics.csv` is linear regression, the lowest validation RMSE. It scored RMSE 4.5235, MAE 3.5671 and R² 0.9493 on the test rows, which makes it a solid fallback. I did not score gradient boosting on the test rows, so that the test set was used only once. Before deploying gradient boosting I would refit it on all 1,020 rows and confirm it on newly delivered parcels.

## Model results (classification)

The stratified split is 840 / 180 / 180 rows. The validation and test sets hold 42 and 41 delayed parcels.

**Validation at the default 0.5 rule** (`outputs/part_c_models.csv`)

| Model | TN | FP | FN | TP | Accuracy | Precision | Recall | F1 |
|---|---|---|---|---|---|---|---|---|
| blind_all_on_time | 138 | 0 | 42 | 0 | 0.7667 | 0.0 | 0.0 | 0.0 |
| logistic_regression | 128 | 10 | 7 | 35 | 0.9056 | 0.7778 | 0.8333 | 0.8046 |
| decision_tree_depth_6 | 128 | 10 | 11 | 31 | 0.8833 | 0.7561 | 0.7381 | 0.747 |
| random_forest_default | 132 | 6 | 10 | 32 | 0.9111 | 0.8421 | 0.7619 | 0.8 |

- **The blind baseline is useless.** Calling every parcel "on time" scores 0.7667 accuracy but catches 0 of the 42 delayed parcels (recall 0.0). Operations would make no calls and no escalations at all. The high accuracy comes only from the fact that most parcels are on time, which is why accuracy alone cannot judge this problem. Every trained model beats it on accuracy (0.8833 to 0.9111) and, more importantly, on recall.
- **The noise columns get a large share of the forest's importance.** In `outputs/part_c_feature_scores.csv`, the five bookkeeping columns receive 0.0462 + 0.0478 + 0.0496 + 0.044 + 0.0377 = 0.2253 of the default forest's importance. That means more than a fifth of the importance goes to random numbers. Impurity-based importance rewards columns with many distinct values, because the trees can find chance splits on them. The F-test is not fooled: all five noise columns fall outside the top 7, at F-ranks 8 (`label_print_batch`, F = 4.5847), 12, 14, 16 and 17, all with F below 10. The weakest of the top seven, `sale_event_flag`, has F = 36.7281. The top 7 are `distance_km`, `hub_tier`, `hub_daily_capacity`, `n_stops`, `promised_hours`, `rain_flag` and `sale_event_flag`.
- **The k table shows that 7 columns is the sweet spot** (`outputs/part_c_selectk.csv`). Validation F1 is:

  | k | 5 | 7 | 10 | 12 | 17 |
  |---|---|---|---|---|---|
  | Validation F1 | 0.6988 | 0.8333 | 0.814 | 0.8049 | 0.8 |

  Keeping only 5 columns drops `rain_flag` and `sale_event_flag`, which are real causes of delay, and F1 falls sharply. Every column added after the seventh is weak or pure noise, and F1 slides back to 0.8 with all 17. So k = 7 keeps every real driver and nothing else.
- **Tuning did not beat the untuned forest** (`outputs/part_c_tuning.csv`):

  | Search | Fits | Best parameters | Best CV accuracy | Validation F1 |
  |---|---|---|---|---|
  | Grid search | 27 candidates × 5 folds = 135 | max_depth 6, min_samples_leaf 1, n_estimators 100 | 0.8952 | 0.775 |
  | Randomized search | 9 candidates × 5 folds = 45 | n_estimators 50, min_samples_leaf 1, max_depth 6 | 0.8905 | 0.7901 |
  | Untuned forest, same 7 columns | 1 | defaults | n/a | 0.8333 |

  There are two reasons the searches lost. First, they maximise accuracy (the default scoring), not F1 on the delayed class, and the grid caps `max_depth` at 8, so it can never pick the fully grown trees of the default forest. Second, the 180-row validation set holds only 42 delayed parcels, so moving a single parcel between caught and missed shifts recall by about 0.024. The F1 gaps of 0.04 to 0.06 between the rows are a handful of parcels. On a validation set this small, a tuning "win" or "loss" is weak evidence. The rule picks the highest validation F1, so the final configuration is `default_forest_same_7_features`: 100 trees, unlimited depth, `min_samples_leaf` 1 (`outputs/part_c_final_config.csv`).
- **The alert threshold is 0.5** (`outputs/part_c_thresholds.csv`). The operations rule takes the highest threshold whose validation recall is at least 0.80, which is 0.5. At 0.5, recall is 0.8333 (35 of 42 delayed parcels caught), precision is 0.7955 and F1 is 0.814. The next step, 0.6, raises precision to 0.8889 but drops recall to 0.7619, below the floor, missing 10 delayed parcels instead of 7. Lower thresholds catch more (recall 0.881 at 0.4, 0.9286 at 0.3) at the cost of precision (0.74 and 0.6964), which means more unnecessary calls. A missed delay costs more than a call, so 0.5 is the most precise threshold that still meets the recall floor.

  The threshold table's F1 at 0.5 (0.814) is lower than the 0.8333 in the tuning table. The rule flags parcels with probability ≥ 0.5, while `predict()` needs a probability strictly above 0.5. A 100-tree forest gives probabilities in steps of 0.01, so a few parcels sit exactly on 0.50 and are flagged here.
- **Test result** (`outputs/part_c_final_test.csv`, a single evaluation at 0.5). TN 125, FP 14, FN 10, TP 31, giving precision 0.6889, recall 0.7561, F1 0.7209 and accuracy 0.8667. Test recall (0.7561, 31 of 41 caught) is below validation recall (0.8333) and below the 0.80 target. With only 41 delayed parcels in the test set, each one is worth about 0.024 of recall, so the gap is about three parcels. Part of the gap is expected: the threshold was chosen on the validation set, so validation recall flatters the model. Recall in production should be expected to sit closer to the test value than to the validation value, which is why it is the first quantity in the monitoring plan below.

**2. Hubs whose tier label is misleading** (`outputs/tier_vs_segment_mismatch.csv`)

| Hub | Tier label | Behaves like | Delay rate | Meaning |
|---|---|---|---|---|
| HUB07 Kolkata | Tier 1 | Watch | 0.14 | Runs like a regional hub (mean distance 304.736 km, 70.76 stops), not a metro hub. The Tier 1 label hides its risk. |
| HUB13 Nagpur | Tier 2 | Escalate | 0.46 | As bad as Patna (0.46). It needs the stretched-hub playbook, not the regional one. |
| HUB15 Kochi | Tier 2 | Escalate | 0.36 | Long lanes (466.514 km) and heavy routes (84.1 stops), like the Tier 3 hubs. |
| HUB22 Dehradun | Tier 3 | Watch | 0.20 | Performs better than its label, like a regional hub. Escalating it would waste hub-manager time. |

The tier label describes a hub's size and capacity, not how it actually performs. **Use the segment, not the tier, to choose the playbook.** `predict_delay.py` already does this. The tier label is also a model input (`hub_tier`, `hub_daily_capacity`), so for these four hubs the classifier is fed a misleading signal. I recommend correcting their labels, or adding the segment as a feature, at the next retrain.

**3. The alert threshold is 0.5.** On the test set, precision is 0.6889, so about **7 of every 10 flagged parcels are really delayed** (about 3 in 10 calls are unnecessary). Recall is 0.7561, so about **7 to 8 of every 10 delayed parcels are caught** (31 of 41), and 2 to 3 of every 10 still slip through without an alert.

**4. Today's batch** (`outputs/new_shipment_actions.csv`). 8 of the 48 new parcels are flagged:

- **6 need a hub-manager escalation**, because they are flagged and their hub is in the Escalate segment: SHP90002 (HUB24), SHP90003 (HUB18), SHP90011 (HUB17), SHP90025 (HUB20), SHP90041 (HUB21) and SHP90046 (HUB21).
- **2 get a proactive customer call:** SHP90005 at HUB22 Dehradun and SHP90007 at HUB09 Jaipur, both in the Watch segment. If the tier label were used, SHP90005 (probability 0.73) would have been escalated as a Tier 3 parcel. The segment correctly sends it to the cheaper action.
- The other 40 parcels need no action.

**5. Why the segments use K = 3** (`outputs/part_d_separation.csv`)

| K | Across-over-within ratio | Cluster sizes |
|---|---|---|
| 2 | 2.894 | 15-9 |
| 3 | 5.3928 | 9-8-7 |
| 4 | 6.3047 | 8-7-5-4 |
| 5 | 6.8866 | 8-7-4-3-2 |

The ratio always rises with K, because more clusters always make same-cluster pairs closer, so the ratio cannot choose K on its own. The big improvement is from K = 2 to K = 3; after that the gains are small. More importantly, K = 4 contains a cluster of only 4 hubs, and K = 5 has clusters of 4, 3 and 2 hubs. A cluster of fewer than 6 hubs is too small to staff and run its own playbook. K = 3 gives three balanced groups (9-8-7), matching the three playbooks operations actually runs.

## Production plan

**(a) Production-readiness characteristics mapped to this repository**

| Characteristic | Where it lives in the repository |
|---|---|
| Accuracy | Validation and test scores are recorded in `part_b_metrics.csv` (test R² 0.9493), `part_c_thresholds.csv` and `part_c_final_test.csv` (test F1 0.7209). The alert threshold is chosen to meet the operations recall rule, not to maximise accuracy. |
| Reliability | `clean_shipments` handles every defect found in the raw export: duplicates, casing and spacing variants, blanks, ₹ text and the 999 kg sentinel. On the 48 new parcels it fills gaps with the stored medians and `new_shipment_actions.csv` has no missing value. Both hub merges use `validate="many_to_one"`, so a duplicated hub row fails loudly instead of silently duplicating parcels. A service type outside Express, Standard and Economy raises an error instead of being guessed. |
| Reproducibility | `requirements.txt` pins exact versions, `generate_data.py` is committed, and every split, model and search uses a fixed `random_state`. A clean clone re-creates every CSV, and two runs of `predict_delay.py` give byte-identical files. |
| Performance (speed) | Scoring loads one pickle and calls `predict_proba` once for the whole batch. Nothing is fitted at scoring time, and the scoring script needs only the files in `models/` and the hub segments. |
| Maintainability | Constants and cleaning and feature code exist once, in `src/shipment_prep.py`, with one script per Part. The chosen model settings are data (`part_c_final_config.csv`) read by `package_model.py`, not numbers copied by hand. |
| Consistency (same preprocessing) | `predict_delay.py` imports the same `clean_shipments` and `build_features` used for training, fills gaps with `models/impute_values.csv` (the historical medians) and orders columns by `models/feature_order.csv`. The feature selector and the forest are saved as one Pipeline, so selection cannot be skipped. |
| Monitorability | `part_d_reload_check.csv` (max reload difference 0.0) verifies the saved artefact. `new_shipment_actions.csv` keeps the probability, flag and action for each `shipment_id`, ready to be joined to actual delivery hours later to measure precision and recall. |

**(b) What to monitor, with triggers**

| Quantity | Reference value | Trigger |
|---|---|---|
| Weekly delayed share of delivered parcels | 0.2317 (`part_a_checks.csv`) | Outside 0.18–0.28 for two consecutive ordinary (non-sale) weeks |
| Weekly share of parcels flagged | 44 of 180 validation parcels flagged at 0.5 (TP 35 + FP 9); 8 of 48 in the new batch | Above 0.35 or below 0.12 in any week |
| Recall on parcels whose outcome is now known | 0.7561 on test | 4-week rolling recall below 0.70: re-pick the threshold, and retrain if that is not enough |
| Precision on the same parcels | 0.6889 on test | Below 0.50: too many unnecessary calls |
| Input health | 0 missing values after cleaning; medians 314.95 km, 1.83 kg, INR 1,121.50 | More than 5% of a batch needing a median fill, or a hub's weekly mean distance moving more than 20% from `hub_profile.csv` |

**(c) Retraining and the sale window**

- **Schedule.**
  - Retrain monthly on a rolling window of recent delivered parcels by re-running Parts A to D: recompute the medians, refit the selector and forest, and re-pick the threshold on a fresh validation slice.
  - Re-cluster the hubs every quarter, because hub behaviour changes more slowly, and review the tier labels at the same time.
  - Retrain early if the recall or delayed-share triggers fire.
  - Before replacing the live model, compare the new model with the current one on the same recent held-out weeks, and keep the previous pickle for rollback.
- **The sale window (15–28 September, `sale_event_flag = 1`).** The sale is a known, planned event, not drift. Delivery hours rise during it (correlation of `sale_event_flag` with `delivery_hours` is 0.1709), and `generate_data.py` adds extra hours for Express in particular.
  - During the sale, compare the delayed share, flag share and recall against the previous sale event, not against ordinary weeks. Otherwise the delayed-share trigger fires every sale and someone retrains on a temporary spike.
  - Keep sale rows in training, with the flag, so the model learns the effect, and make sure every training window contains at least one sale period.
  - For a brand-new event with no history, set wider temporary trigger limits for its duration.
- **What data drift would look like here.**
  - Input drift: the distance mix moves toward longer lanes (more parcels in the 401-600 km and 601+ km bands, which delay at 0.4364 and 0.8523), routes get more stops, the service mix shifts toward Express, the COD share changes, or hubs change capacity.
  - Concept drift: the same inputs start giving different outcomes. For example, a hub that upgrades its fleet would show falling precision for its parcels and would move to a lower segment when re-clustered.

## Limitations

1. **Synthetic data.** Delivery hours come from a known formula plus Gaussian noise. Real shipment records would have messier relationships, unrecorded causes (traffic, address quality, rider absence) and new kinds of data defects. The scores here (test R² 0.9493, test F1 0.7209) are best cases, not what to expect in production.
2. **Few delayed parcels to evaluate on.** The test set has only 41 delayed parcels, and one parcel is worth about 0.024 of recall. With test recall at 0.7561 against 0.8333 on validation, it is not possible to tell whether the model truly misses the 0.80 target or the split was unlucky.
3. **The threshold is tuned on one validation split.** It was picked on 180 rows with 42 delayed parcels, and a different split could have picked 0.4 or 0.6. Choosing it from cross-validated probabilities on the training rows would be more stable.
4. **Hub labels are used as features.** `hub_tier` and `hub_daily_capacity` are static labels that are wrong for four hubs, so the model learns part of the tier effect from mislabelled hubs.
5. **Short history.** The data covers 90 days (July to September 2026) with a single sale event: no festive season, no monsoon variation, and no year-on-year comparison for the sale-window rule.
6. **Segments rest on 24 points and four averages.** K = 3 is stable, but hubs near a boundary could switch segment after a few more delays, for example HUB14 Coimbatore (0.24) and HUB22 Dehradun (0.20).
7. **Regression model choice.** The pinned rule sent linear regression to the test set, while cross-validation prefers gradient boosting. Only one of the two has a test score.
